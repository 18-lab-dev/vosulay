# vosulay runtime architecture

## Runtime composition

The application has one native process with two closely coupled implementation halves:

1. [`src/main.rs`](../../src/main.rs) collects command-line arguments, serializes them as JSON, and calls the C++ Qt entrypoint exposed by [`src/ffi.rs`](../../src/ffi.rs).
2. [`src/qt/qt_shell.cpp`](../../src/qt/qt_shell.cpp) creates the Qt application, parses options, configures Chromium/WebEngine, creates the overlay window, and runs the event loop.

The bridge is generated by `cxx` from the declarations in [`src/ffi.rs`](../../src/ffi.rs). [`src/qt/bridge.h`](../../src/qt/bridge.h) supplies the Qt-side `QObject` used by `QWebChannel`. Rust-facing calls cover manager document generation, configuration load/save, counter fetching, and vosu URL construction; C++ calls `run_qt_application` to own the native lifecycle.

## Embedded manager UI

[`src/ui.rs`](../../src/ui.rs) includes [`assets/manager.html`](../../assets/manager.html), [`assets/manager.css`](../../assets/manager.css), and [`assets/manager.js`](../../assets/manager.js) at compile time. It replaces a bootstrap marker with escaped CSS and JavaScript string literals before passing the complete document to `QWebEngineView::setHtml()`. This makes runtime startup independent of the working directory and prevents embedded `</script>` content from terminating the bootstrap script.

The frontend maintains the editing state, renders profile placements, and sends JSON messages through the bridge. The Qt shell returns configuration, counter metadata, file selections, editing state, save results, and errors. The [configuration model](../domain/configuration.md) is therefore shared conceptually by Rust persistence and JavaScript normalization, while the [integration layer](../integrations/vosu-and-overlays.md) supplies external counter and overlay sources.

Counter frames receive one narrowly scoped compatibility script from [`counterMetadataScript`](../../src/qt/qt_shell.cpp). WebEngine installs it in the MainWorld at DocumentCreation and runs it on subframes, but it acts only when the frame origin exactly matches the configured vosu origin. It preserves any existing string-valued `window.COUNTER_PATH`; otherwise it derives the counter folder from the frame pathname, decodes each path segment, and sets the global only when the resulting folder is non-empty.

## Window and platform behavior

The shell uses a frameless, transparent, always-on-top `QWebEngineView`, a system tray icon, and a local IPC server. Editing mode makes the window interactive; display mode makes it click-through. On Wayland, LayerShellQt places the surface in the overlay layer with no exclusive zone and disables keyboard interaction unless editing. On X11, Qt input transparency and window masks provide the corresponding click-through behavior.

When no overlays are active, the WebEngine page may be hidden/discarded; when overlays remain active but the window is hidden, the page can be frozen. These lifecycle optimizations are implemented in the C++ shell and must be considered when changing visibility or bridge callbacks.

Local HTML selection is also owned by the Qt shell. While the XDG Desktop Portal file chooser is active, the shell hides the overlay and releases input capture, then restores its previous visibility and the input state appropriate to the current editing mode. It accepts only a local `file://` HTML/HTM file that is a readable regular file and can be opened read-only. The selected file is exposed through a capability-bearing `vosulay-overlay` URL; the scheme handler authorizes that capability for one canonical directory root and serves only canonical, readable regular files confined beneath it. The detailed boundary is documented in [vosu catalog, overlay sources, and local IPC](../integrations/vosu-and-overlays.md).

## Concurrency and lifecycle

Network counter discovery and configuration saves run on `QThread` workers rather than blocking the Qt UI thread. Counter responses carry generation state so stale results are ignored. Saves use a pending-save slot, debouncing/serializing work while shutdown guards suppress callbacks during teardown. Changes to worker ownership or callbacks should be checked against the [testing guidance](../testing/guidance.md).

## Build boundary

[`build.rs`](../../build.rs) is part of the architecture: it discovers Qt modules with pkg-config, runs `moc` for the bridge, compiles C++17 through `cxx-build`, and uses a generated CMake probe to locate `LayerShellQt::Interface`. See [build and run operations](../operations/build-and-run.md) before changing native includes, bridge signatures, or platform setup.
